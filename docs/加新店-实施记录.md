### ② 云端接口

**`tasks`（手机端）**
- **`newShopCheck`** → `{ area, bizCircle, cands[前3], block, sameName, recLimit, recEnabled, photoLimit }`
  - 防重复：200 米内查同电话 / 同名（坐标范围粗筛 + 精确算距离）
  - 自动识别：**半径 100 米内按 1/距离 加权投票**（区域用"行政区"、商圈用 `regionName`），取前 3 候选
    —— 与 `_scratch/loo2_biz.py` 的留一验证口径一致（R=100 / 1d / 前 3 覆盖 99.4%）
  - 识别数据**从云端集合查**（不再读包内 JSON）：`pullNear()` 按 `lat/lng` 范围（±0.0015° ≈ 165 米）拉点，拉满 1000 条自动收缩范围重拉
  - **⭐ 顺带返回 `recLimit`/`recEnabled`/`photoLimit`** —— 新店页**没有任务**，拿不到任务上快照的这几个配置，
    只能从 `settings`（`loadSettings()`）读回来，前端因此**不必写死**档位（后台一改就跟着变）
- **`newShopSubmit`** → 建档（`customers` 一条）
  - 写三层骨架 `city/district/bizCircle` + `region`（与 `importdata.deriveGeo` 同一口径）
  - 坐标：`lat/lng`（GCJ-02）＋ `wgsLat/wgsLng`（现场采的 WGS-84 留底；**手动修正过位置则为 0 = 无原值**）＋ `coordSource:'field'`
  - 标记：`source:'field'` ＋ `mallPending:true`
  - 证据：`photos`（店面照 fileID）＋ `audios`（`[{fileID, duration, text}]`）
  - 服务端二次查重 + 店面照必拍校验
- **`custDetail`**：返回体白名单加了 `mallPending`（手机端据此显示胶囊）

**`adminapi`（后台）** → 新增 2 个 action（**`ACTIONS` 白名单已同步补**，坑 32）
- **`fieldList`** `{ page, pageSize, q }` → 待商城建档列表（店名/电话/地址/区域商圈/坐标/店面照/谁录的/何时录/商城是否已有档案）
- **`fieldDone`** `{ id }` → 手工取消"待商城建档"标记

**算法实测**（取 6 个真实点回查）：5 个与期望完全一致；第 6 个 top-1 差一位（农贸城 vs 稠关小区），但 **top3 里包含正确答案**。

## 四、关键实现点（改之前先看）

1. **识别不依赖腾讯 API**：不做逆解析（省掉 key 白名单的坑）—— 点评数据里本来就有"行政区"和 `regionName`，直接近邻投票。
2. ⭐ **2026-09-28 晚（方案 B）：数据从云函数包搬到云端数据库集合 `biz_index`**
   - 起因：3.45MB 打进云函数包 → **每次部署都多传 3.45MB**；且以后扩城市必然超过云函数 **10MB** 上传上限
   - **导入走过的路（留给下次参考）**：
     ① `importdata` 云函数逐条写 7 万条 → **失败**（`-601008` 云函数超时 + `EXCEED_RATELIMIT` 环境限流，0 条写入）
     ② 改走**官方 HTTP API 批量导入** → **成功**（`admin/tools/import_biz_api3.js`：取 token → `tcb/uploadfile` 拿上传链接 → POST 上传到云存储 → `databasecollectionadd` 建集合 → `databasemigrateimport` 触发导入）
     - ⚠️ **两个坑**：a) 云存储里的**文件名必须是 `.json` / `.csv`**（用 `.jsonl` 报 `-501007 invalid import filename`）；b) 集合**不存在**时报 `-501018 no such collection`
   - 索引：`admin/tools/add_index.js` 新增 `biz_index` 的 `lat + lng` 复合索引（没索引会全表扫 7 万条）
   - 效果：**`tasks` 云函数从 ~3.5MB 回到 62KB**
   - 相关：`importdata` 新增 `biz_index` 类型；`init` 的 `COLLECTIONS` 已加 `biz_index`
3. **数据里有 (0,0) 空坐标**（源数据带的）→ 导入脚本与云函数**双保险**跳过（`if (!p.lat || !p.lng) continue`）
4. **小程序 `require` 不支持 `.json`** → 词表必须包成 `.js`（`utils/newshop_words.js`）。
5. 商圈候选是**前 3 个都给人点**，不是只给一个答案（老板口径：「自动填的东西要给依据 + 允许改」）。
6. **行尾**：`admin.html` 与 `pages/customer/customer.js` 都是 **CRLF 系** —— `edit_file` 会把 CRLF 写成裸 LF，
   本轮实测：`admin.html` 带进 38 处、`customer.js` 带进 2 处 → 用 `_scratch/check_field_page.js --fix` 修
   （⚠️ 修法必须用 `/\r?\n/g → '\r\n'`；用 `/(^|[^\r])\n/` 会在**连续两个裸 LF** 时漏掉一个）。
7. **自检脚本 `_scratch/check_field_page.js`**（只读，8 块）：
   `--fix` 先行尾修复 → ①行尾字节数 ②6 个 JS 语法 ③admin.html 内嵌 JS ④「待商城建档」接线 18 项
   ⑤WXML 标签配对 ⑥`d.*` 字段定义 ⑦newshop 的 32 个事件 / 44 个顶层字段 ↔ JS 对照 ⑧录音卡接线 12 项
8. ⚠️ **写自检脚本时踩过的三个"误报"**（下次写同类工具别再犯）：
   ① **注释里的标签**也算数（wxml 注释里写了 `<map>` → 误报 `map:4/1`）→ **先剥 `<!-- -->` 再数**；
   ② **自闭合标签**（`<input />`、`<image />`）本来就没有 `</input>` → **只数开标签**；
   ③ **`wx:for-item="g"` 这种自定义循环变量**不是 data 字段 → 要**动态收集**再排除（只排除 `item`/`index` 不够）。
   另外：行尾修复正则在**连续两个裸 LF** 时会漏一个（见第 6 条）。
