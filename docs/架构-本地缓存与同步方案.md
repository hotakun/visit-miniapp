## 〇、一句话

> **云端是唯一真相源；本地只是快照 + 加速层。列表走本地，详情实时拉，热数据不缓存。**

---

## 一、核心原则（⭐ 五条铁律，后续开发不得违反）

| # | 铁律 | 说明 |
|---|---|---|
| 1 | **云端是唯一真相源** | 写操作**永远先写云端**，绝不允许"先改本地再同步" |
| 2 | **本地只是快照** | 本地缓存随时可丢、可重建；丢了不影响正确性，只影响速度 |
| 3 | **热数据不缓存** | 业务员实时位置、拜访中等**分钟级**数据，永远实时拉 |
| 4 | **列表走本地，详情实时拉** | 列表/地图/勾选用**轻量字段**；点开详情/编辑**实时拉单条** |
| 5 | **缓存必须显示数据时间** | 每个缓存在界面显示「数据截至 xx:xx」，让人知道新旧 |

## 二、数据四分类（分类决定策略）

| 类别 | 例子 | 变化频率 | 策略 |
|---|---|---|---|
| **A 冷数据** | 客户档案、订单、明细、批次、任务定义 | 天 / 周 | **本地缓存** + 每天全量对账 |
| **B 温数据** | 拜访状态、任务进度、批次状态 | 小时 / 天 | **本地缓存** + **增量拉** |
| **C 热数据** | **业务员实时位置**、拜访中状态 | **分钟** | ⚠️ **实时拉，绝不缓存** |
| **D 统计** | 仪表盘数字、日报 | 按需 | **本地算**（数据已在本地）；超大数据可云端预聚合 |

**地图客户点 = A + B 混合**（坐标是 A、拜访状态是 B）→ 所以缓存记录**必须带 `updatedAt`**，才能增量拉。

## 三、同步机制（三档，各管一段）

| 档 | 触发时机 | 用途 | 备注 |
|---|---|---|---|
| **① 全量拉** | 首次 / **每天一次** / **手动更新按钮** | **兜底 + 对账（能发现"删除"）** | 分片拉（云函数单次返回上限 100KB） |
| **② 增量拉** | **每 30~60 秒**（轻量轮询） | 拉 `updatedAt > 上次` 的记录 | 只回几十条，很快 |
| **③ 写后回写** | 用户一改就做 | 云端成功 → **本地立即更新**（不等轮询） | 见 §四 |

### 3.1 关于"云端主动分发更新缓存"（老板提出，已确认落法）

**技术事实**：云函数**无法主动推送**到本地后台（云开发不支持反向长连接）。
**等价落法（已定）**：

> **轻量轮询 `syncTick`**：后台每 30 秒调一次，**只回"谁改了什么"的最小摘要** → 有变化才拉那几条。

体感与"主动分发"一致（30 秒内自动更新），实现简单、不会漏。

### 3.2 ⚠️ 必须先知道的坑：**删除同步**

**增量拉拉不到"删除"**（被删的记录不会出现在结果里）。**已定方案**：

> **增量拉管"改"，每天全量管"删"** —— 全量时比对 `_id` 集合，本地多出来的即为已删。

（备选：把现有 `deleteCustomers` 等一串硬删改成"软删 + 墓碑"—— 改动面大，**性价比不如每天对账**，本期不采用。）

## 四、写路径（"双向同步"的真实含义）

```
用户改数据（新增/修改/建批次/建任务）
        ↓
① 先写**云端**（adminapi.xxx）→ 返回 { ok, updatedAt }
        ↓
② 成功后**本地立即更新**（UI 马上反映，不等下次轮询）
        ↓
③ 失败 → 报错 + 本地不动（绝不产生"本地改了云端没改"）
```

★ **本质是"单向写 + 双向读"**：写入只有云端一个入口，读取才是"本地优先"。

**批量操作天然只写一次**：`createManualBatch({ customerIds: [...1000 个] })` 是**一次云调用**，不是 1000 次。
→ 所以"本地勾选 1000 家 → 点建批次"之所以快，是因为 **UI 在本地、写只发一次**。

## 五、体积分层（列表层 vs 详情层）⭐ 关键

客户档案有 **47 列**，5 万条 = **100MB+**，**绝不能整个缓存**。分两层：

| 层 | 内容 | 存在哪 | 用途 |
|---|---|---|---|
| **列表层** | `_id / 店名 / 坐标 / 城市 / 商圈 / 拜访状态 / 客户编号 / updatedAt`（≈10 字段，≈100 字节/条） | **本地缓存** | 客户管理列表、地图点、建批次勾选 |
| **详情层** | 全部 47 列 + 订单 + 备注 + 照片 | **实时拉单条**（`getCustomerDetail` 已有） | 客户详情页、编辑 |

**容量估算**：5 万条 ≈ **5MB**、20 万条 ≈ 20MB（读文件，无压力）。

## 十、M1 详细设计（本期开工）

**目标（两件事）**：
1. **启动初始化** —— 后台启动 / 当天首次打开时，把"列表层数据"准备好（**首次全量、之后增量**）。这是**通用 `store` 的第一块**；
2. **战况监控地图**的客户点**全部来自本地缓存**，拖动/缩放**不请求云端**。

> ⚠️ M1 虽叫"只管地图"，但**初始化拉的数据本身是通用的**（= 客户列表层）→ M2 切客户管理页时**不用重拉**，只是换个消费方。

**启动初始化（数据就绪门）**：

```
后台 server.js 启动
      ↓ 检查缓存是否过期（自然日）
      ├─ 没过期 → 不管（静默）
      └─ 过期/没有 → 【后台静默拉】：首次全量（分片） / 之后增量（updatedAt > lastSync）
      ↓
管理员打开后台页面
      ├─ 数据已就绪 → 直接进
      ├─ 拉取中     → 进度「正在准备数据 32%」+【先用现有数据进入】
      └─ 拉取失败   → 明确提示 +【重试】/【先用旧数据进入】
```

★ **原则：门禁是"帮你不卡"，不是"挡你进门"。**

### 10.1 数据流

```
每天首次打开后台
      ↓
server.js 检查 admin/cache/map-points.json
      ├─ 是今天生成的            → 直接用
      └─ 不存在 / 过期 / 手动刷新 → 调云端分片拉全量 → 写文件
      ↓
前端 GET /mapPoints → 一次性拿到全部轻量点
      ↓
拖动 / 缩放 → 纯本地：筛视野 + **本地聚合** → 画图（★不请求云端）
      ↓
「🔄 更新地图数据（截至 MM-DD HH:mm · N 万家）」→ POST /mapPoints/refresh → 重拉覆盖
```

### 10.2 轻量点字段（`admin/cache/map-points.json`）

```json
{ "v": 1, "syncedAt": 1758931200000, "count": 52000,
  "points": [ { "i":"c347", "n":"莎莎秘制卤味", "la":28.9708, "ln":120.1545,
                "s":2, "c":"金华", "d":"永康", "b":"古山镇" } ] }
```

| 键 | 含义 | 备注 |
|---|---|---|
| `i` | `_id` | 点详情时用它实时拉 |
| `n` | 店名 | |
| `la` / `ln` | 纬度 / 经度 | 显示纬度在前，与现有口径一致 |
| `s` | 拜访状态 | **数字**：0 无任务 / 1 待拜访 / 2 拜访中 / 3 已拜访（省体积） |
| `c` / `d` / `b` | 城市 / 区域 / 商圈 | **本地聚合要用** |

**体积**：≈100 字节/条 → 5 万条 ≈ 5MB。

### 10.3 云函数（`adminapi` 新增 `custMapPoints`）

- 入参：`{ cursor, limit }`（分片游标；`limit` 默认 1000）
- 出参：`{ ok, points: [...], next: <游标|null>, total }`
- **只回 §10.2 的轻量字段**（不要用 `listCustomers` 拉 47 列）
- ⚠️ **单次返回上限 100KB** → 分片必须 ≤1000 条
- 必做（项目坑 32）：补 `ACTIONS` 数组

### 10.4 后台 `server.js`（新增 3 个接口）

| 接口 | 作用 |
|---|---|
| `GET /mapPoints` | 读缓存文件返回；**文件不存在/过期 → 自动触发一次拉取**（带进度状态） |
| `POST /mapPoints/refresh` | 强制重拉 + 覆盖文件 |
| `GET /mapPoints/status` | 返回 `{ syncedAt, count, running, progress }`（前端显示进度/时间） |

- 拉取方式：**循环调 `custMapPoints` 直到 `next` 为 null**（分片 1000 条 ≈ 50 次；一天一次，30 秒左右可接受）
- **失败不清空**：拉取失败时保留旧文件，前端用旧数据 + 黄字提示

### 10.5 前端（`admin.html`）

| 改动 | 说明 |
|---|---|
| `loadCustData` | 改为**读 `/mapPoints`**（不再调 `listCustomers`） |
| **聚合改本地算** | 遍历本地点做 group（≈1~2ms），替换对 `custGeoAggregate` 的调用；**该云函数保留作兜底** |
| 视野过滤 | **保留**（本地筛，更快） |
| 更新按钮 | 战况监控工具栏加「🔄 更新地图数据（截至 …）」，点击调 `/mapPoints/refresh` |
| 时间戳 | 地图角落显示「数据截至 MM-DD HH:mm · N 万家」 |
| 首次拉取 | 显示「正在准备地图数据…（N/总数）」进度 |

### 10.6 M1 验收标准

1. 当天首次打开战况监控 → **自动**准备好缓存（有进度提示）
2. 之后**拖动/缩放地图，网络面板 0 请求**，画面跟手
3. 小比例尺出**数字气泡**、街道级出**真实点**（沿用上一版分级聚合的行为）
4. 点「更新地图数据」→ 重新拉取 → 时间戳刷新
5. 拉取失败时**仍有图**（用旧缓存）+ 提示
6. **业务员实时位置不受影响**（仍实时拉）

## 十三、缓存策略（⭐ 2026-09-27 老板定：**按需用缓存** —— 大胆，但不画蛇添足）

> **老板原话（前半）**：
> "**要善于利用各种缓存，本地缓存、浏览器缓存、内存缓存，你的构思应该充满创意。在既能保证数据安全，又能方便人员操作的情况下进行大胆构思。**"
>
> ⚠️ **老板当场纠正（后半，同样重要，别漏）**：
> "**不是说要主动用满，而是根据情况来安排，没必要用满的就不用画蛇添足。**"

### 13.0 总原则：**按需使用**

| 问自己 | 判断 |
|---|---|
| 是不是**高频、重复、开销大**？（如：每次全量拉 2000+ 家客户、每拖一次地图就画几十张 canvas 图标） | → **该用** ✅ |
| 是不是**一次性、数据本来就小、本来就快**？ | → **别加**（为缓存而缓存 = 画蛇添足）❌ |
| **能不能真省时间 / 省请求 / 让人更顺手**？ | → 答不上来 → **别做** ❌ |

### 13.1 三层缓存（**按需选层**，不是每层都要上）

| 层 | 载体 | 放什么 | 生命周期 |
|---|---|---|---|
| **L1 内存** | 浏览器 JS 变量 / Map | 会话热点：客户点列表、聚合结果、**canvas 图标**、翻过的分页 | 关页即失效 |
| **L2 浏览器存储** | `localStorage` / `IndexedDB` | 跨刷新保留：下拉选项、上次筛选、UI 偏好、缩略图 | 分钟 ~ 天 |
| **L3 后台本地文件** | `admin/cache/*.json` | 大数据快照：客户点、批次、任务 | 天（按自然日） |
| **L4 自己的数据库** ⭐ | **服务器 PostgreSQL（`juhuo` 库）** | **客户/订单的只读镜像** —— 后台改从这里读，不再打云开发（2026-10-09 落地，详见 `项目交接-当前进度.md` §0.0z12） | 分钟级（同步器每 5 分钟拉增量） |

### 13.2 已落地（M1 期间）

- **图标缓存** `aggIconCache` —— 同一数字只画一次 canvas（**治"地图卡 / 缺块"的关键**）
- **聚合结果缓存** `custAggCache`（60 秒，key = 层级 + 视野 + 条数）
- **客户点缓存** `admin/cache/map-points.json`（后台启动 / 当天首次自动预热）
- **缓存版本号** `VERSION`（字段结构变了就 +1 → 旧缓存自动作废重拉；**当前 = 3** —— M2b 把轻量点字段从 12 项扩到 20 项）
- **写后回写** `POST /mapPoints/patch`（M3）：改完（备注/坐标/字段/删除/建批次）只把那几条同步进缓存文件，不等全量刷新 —— 前端同步更新内存副本，翻页/筛选立刻准
- **列表缓存** `trackCustCache`（60 秒）

### 13.3 可继续做的（创意清单，按收益排序）

| 想法 | 收益 |
|---|---|
| **下拉选项缓存**（`custGeoOptions` 存 L2，每天一次） | 少调云函数、筛选框秒开 |
| **翻过的页留内存**（客户管理第 2 页 → 来回切秒开） | 翻页无等待 |
| **写后回写**（改完客户 → 本地立即更新，不等下次拉） | 操作无感 |
| **空闲预取**（后台空闲时预拉可能看的下一页/下一个层级） | 提前备好 |
| **表格虚拟滚动 + 本地筛选** | 5 万行也顺 |
| **缩略图 / 图片 L2 缓存** | 客户详情秒开 |
| **记住"上次看到哪"**（筛选条件 / 滚动位置 / 选中的人） | 续着用，不用重新点 |

### 13.4 ⚠️ 安全红线（**创意不能越线**）

1. **写永远先写云端** —— 本地只是缓存，**不是数据源**（铁律第 1 条）
2. **敏感信息不进缓存**（密码 / token / appsecret）
3. **云端是唯一真相源** —— 缓存可丢、可重建
4. **每个缓存都要有失效策略**，并在界面上显示「**数据截至 xx:xx**」
5. **多人 / 多机**场景下，缓存不得成为"第二真相"（冲突一律以云端为准）
