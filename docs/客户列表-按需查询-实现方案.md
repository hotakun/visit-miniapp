# 客户列表「按需查询」改造 · 实现方案

> 目标：把「后台打开客户列表要下 88 MB / 等 60 秒」变成「首屏 < 300 ms、翻页 < 120 ms」，
> 并且**任何异常都能退化到可用状态**，不出现"白屏 / 空表 / 数据对不上"。

- 文档版本：v1（2026-10-23）
- 状态：**待评审，未动工**
- 影响范围：`admin/server.js`、`admin/store.js`、`admin/admin.html`、`server/pgapi.js`
- 不改：云函数、小程序端、PG 表结构

---

## 1. 结论摘要

| 项 | 现在 | 改造后 |
|---|---|---|
| 客户列表首屏 | 88.3 MB / **60.4 s**（实测） | **< 300 ms**（一页 50 条，约 30 KB） |
| 翻页 | 前端数组切片（但前提是全量已下载） | 服务端分页，**< 120 ms** |
| 城市/区域/商圈下拉 | 从 17.9 万点现算 | 服务端 facet 接口，**< 50 ms** |
| 浏览器内存 | 300~500 MB（17.9 万对象） | **< 100 MB**（只留当前页 + 少量缓存） |
| 服务器内存 | 已加载 88 MB 缓存 | 不变，另加索引约 **40 MB** |
| 接口 | `/mapPoints` 全量 | 新增 `/points/query`、`/points/facets`（**保留** `/mapPoints` 作兜底） |

**核心原则：服务端是唯一数据源，浏览器不再持有全量。**

## 2. 背景与实测数据

```
GET /mapPoints   → 88.3 MB, 60.4 s（未压缩，浏览器还要 JSON.parse 17.9 万个对象）
GET /points/query?batchId=… （3,115 点）→ 232 KB / 66 ms（已上线，gzip 生效）
GET /pgApiUrl/batchMembers?batchId=…     → 107 KB / 249 ms
```

数据库规模：`customers` 179,138 行；`batch_members` 1,525 行（2026-10-23 清理后）。

为什么会慢：`store.read()` 把整份 `map-points.json` **一次性序列化**给浏览器；列表页在浏览器里
`filter → slice` 分页。数据量到 18 万后这条路的成本随数据量线性增长，且每次刷新都要重来。

## 3. 目标 / 非目标

### 3.1 目标

1. 客户列表、批次详情列表**首屏秒开**，不再下载全量。
2. 筛选（城市/区域/商圈/关键词）、排序、翻页全部在服务端完成。
3. 行为与现在**逐条对齐**（同一筛选条件下，列表内容、总数、排序结果必须一致）。
4. 任一依赖不可用时，**降级到可用**并明确告知用户，不静默出错。

### 3.2 非目标（本次不做）

- 不改云函数、不改 PG 表结构、不动小程序端。
- 不做多用户/权限体系。
- 不做实时推送（仍靠 15 秒轮询指纹判断缓存是否更新）。
- 不重写"地图选点""战况地图"等已改造过的入口。

## 5. 目标架构

```
浏览器
  ├─ GET  /points/facets?scope=…        → 城市/区域/商圈/批次下拉选项
  ├─ POST /points/query  {filters, sort, cursor, size} → 一页数据 + total
  └─ POST /api {action:'custPageAgg'}   → 本页聚合列（沿用现有接口，不改）
        │
server.js
  ├─ pointsIndex()     ← 惰性构建，缓存于 store 快照对象
  ├─ pointsQuery()     ← 过滤 / 排序 / 游标分页
  └─ 依赖：store.read()（内存）+ pgapi（批次归属）
        │
PostgreSQL（仅批次归属）
```

## 6. 接口设计

### 6.1 `POST /points/query`（已存在，本次扩展）

请求：

```jsonc
{
  "ids": ["..."],          // 可选，按 id 批量取（最高优先级）
  "batchId": "…",          // 可选，批次成员（走 PG 的 batch_members）
  "bbox": [minLng,minLat,maxLng,maxLat],  // 可选，地图视口
  "q": "沙县",              // 可选，关键词（店名/编号/电话/地址）
  "city": "金华市",         // 可选
  "district": "永康市",     // 可选
  "biz": "古山镇",          // 可选
  "mode": "mall",          // 可选，ct 字段过滤
  "unbatched": true,       // 可选，只要未分批
  "sort": "name|created|lastOrder|visitCount",  // 默认 updated
  "dir": "asc|desc",
  "cursor": "…",           // 游标（推荐）；与 page 二选一
  "page": 1, "size": 50,   // 页码模式（兼容用）
  "fields": ["i","n","la","ln","mj","lo"],  // 可选，裁剪字段
  "facets": false          // 需要时返回 facets
}
```

响应：

```jsonc
{
  "ok": true,
  "total": 12345,          // 满足条件的总数（batchId 时 = PG 权威成员数）
  "count": 50,             // 本页条数
  "points": [ … ],         // 与 /mapPoints 同构的短键对象（前端 custLocalRow 直接复用）
  "nextCursor": "…",       // 下一页游标；null = 没有下一页
  "ms": 12,                // 服务端耗时（排查用）
  "from": "index|pg|fallback",  // 数据来源，前端可据此提示"批次归属可能滞后"
  "syncedAt": 1792629891497     // 缓存快照时间
}
```

### 6.2 `GET /points/facets`

```jsonc
{
  "ok": true,
  "cities": ["金华市","杭州市"],
  "districts": {"金华市": ["永康市","武义县"]},
  "bizCircles": {"金华市|永康市": ["古山镇","芝英镇"]},
  "batches": [{ "id": "...", "name": "…", "count": 1283 }],
  "counts": { "all": 179138, "mall": 170000, "unbatched": 250 },
  "syncedAt": 1792629891497
}
```

- 由索引一次性算出（首次 ~200 ms，之后缓存，缓存失效跟着 `syncedAt` 走）。
- **注意**：facet 只统计"未删除"客户。

### 6.3 分页方式：**游标优先，页码兼容**

- 游标 = `base64(排序键值 + id)`，稳定、不重不漏（见 §9.5）。
- 页码模式保留给"跳页"场景，但内部会**限制最大偏移**（见 §10.6）。

## 7. 索引设计

构建一次，挂在缓存快照上（`_ptIdxFor === points` 时复用）：

| 索引 | 结构 | 用途 | 构建成本 |
|---|---|---|---|
| `byId` | `Map<string, point>` | id 批量取、patch 定位 | ~25 ms / 18 万 |
| `byBatch` | `Map<batchId, point[]>` | 兼容旧 `bi` 路径 | ~30 ms |
| `searchMap` | `Map<归一化串, point[]>` | 关键词（店名/编号/电话） | ~400 ms |
| `sorted[name/created/lastOrder]` | `point[]`（惰性排序） | 排序+游标 | 首次 ~150 ms，按需 |
| `facet` | `{cities[], districts{}, biz{}}` | 下拉选项 | ~60 ms |
| `grid` | `Map<cell, point[]>` | 地图 bbox（已有实现） | ~40 ms |

**内存预算**：179k 点 ×（索引指针 + 归一化串约 120 B）≈ **35~45 MB**。可接受；如果吃紧，
`searchMap` 可改为"只在首次搜索时构建"，并在 10 分钟无搜索后释放。

**归一化规则**（关键词匹配必须统一，否则"搜不到"）：

1. 全角 → 半角；2. 大写 → 小写；3. 去首尾空格、连续空格压成一个；
4. 店名前缀编号（如 `c602`）单独入索引，允许 `c602`、`602`、`C602` 命中；
5. 电话：去空格/短横线后再入索引。

## 8. 一致性设计（最容易出错的部分）

### 8.1 唯一真相

- **服务端内存缓存**（`store.read()`）是列表的唯一数据源。
- 写操作（改客户、删客户、移出批次）成功后：
  1. `store.patch()` 就地更新内存；
  2. **索引失效**：`_ptIdxFor = null`（下次查询自动重建，18 万约 25 ms）；
  3. 前端当前页**主动重拉**（列表页在写操作回调里 `loadCustomers()`）。

### 8.2 读期间被写：用快照引用

`pointsQuery` 开头 `const pts = store.read().points` 拿**数组引用**；
`store.write()` 是"整对象替换"（新数组），所以进行中的查询持有旧快照，**不会读到半更新状态**。
索引按 `points` 引用缓存，新旧快照各自独立。

### 8.3 与 PG / 云端的差异

- **批次归属**以 PG `batch_members` 为准（本地 `bi` 字段已证实失真：永康曾只有 721/3116）。
- PG 每 5 分钟同步一次 → 批次人数最多滞后 5 分钟。响应里带 `from: "pg"`，
  若 PG 不可用则 `from: "fallback"`，前端在列表上方显示一条灰色提示：
  「批次归属来自本地快照，可能滞后最多 5 分钟」。

### 8.4 缓存预热中（`warming`）

`store.isFreshToday()` 为 false 时会后台全量拉取，此时内存里可能是**空或旧数据**：

- `pointsQuery` 检测 `store.status().syncing && !points.length` → 返回 **503**
  ```json
  { "ok": false, "code": "WARMING", "progress": { "done": 38000, "total": 179138 } }
  ```
- 前端显示进度条「正在准备客户缓存 3.8万/17.9万」，**每 2 秒重试**，不报错、不白屏。
- 有旧数据（非空）时**照常返回旧数据**，只在角落显示「数据更新中」。

## 9. 前端改造

### 9.1 列表页（`loadCustomers`）

```
旧：ensureCustLocal() → 内存 filter → slice → render
新：POST /points/query {filters, sort, cursor, size} → render
```

- 保留 `custFilter` 结构，新增 `cursor`、`reqId`（防竞态）。
- 翻页：`nextCursor` 前进 / `cursorStack` 回退（上一页）；页码模式保留但只用于跳页。
- 加载态：表体显示「加载中…」；**超过 3 秒**追加「网络较慢，可点重试」。
- 错误态：表体显示错误条 + 「重试」按钮，**保留上一次成功的数据**（不清空）。

### 9.2 下拉选项（`loadCustGeoOptions`）

改为 `GET /points/facets`，缓存到内存（`custGeoLoaded`），写操作后置 `false` 重取。

### 9.3 聚合列

`custFillPageAgg(rows)` **不改**（本来就按页调云端）。但要加一条：**失败时保留空值，不阻塞渲染**。

### 9.4 竞态与取消

- 每次请求带 `reqId`；响应回来时 `reqId !== 当前` 直接丢弃。
- 用 `AbortController` 取消上一请求（快速连续翻页时）。
- 页面切换（如从列表跳到详情）时 abort 未完成请求。

### 9.5 分页漂移（**必须解决**）

页码分页在"边翻边改数据"时会重复/漏行。所以：

- 列表默认用**游标分页**（`cursor` = 最后一条的排序键 + id）。
- 光标分页的排序键必须**唯一且稳定**：`(sortValue, id)` 二级排序。
- 用户点"跳页"时用页码模式，并在响应里返回 `total` 供计算总页数；
  若两次请求间 `total` 变化 > 5%，前端提示「数据已更新，已回到第 1 页」并重置。

### 9.6 不再需要的全量下载

`ensureCustLocal()` 保留但**列表页不再调用**（A 类已改服务端）；B/C 类按需调用。
新增开关 `localStorage['adm.fullCache']='1'` 供排查时强制全量。

## 10. 失败场景与应对（逐条）

| # | 场景 | 表现 | 应对 |
|---|---|---|---|
| 10.1 | 服务未启动 / 端口不通 | fetch 失败 | 前端顶部红条「管理后台服务未运行」+「重试」；不自动重试风暴（退避 2s/5s/10s） |
| 10.2 | 缓存预热中（空） | 503 WARMING | 进度条 + 2 秒轮询，见 §8.4 |
| 10.3 | 缓存文件损坏/版本不符 | `store.read()` 返回 null | server 自动触发全量重拉；期间返回 503 WARMING；**绝不返回空表** |
| 10.4 | 索引构建超时（> 5s） | 首次查询变慢 | 查询超时阈值 15s；超时返回 `code: INDEX_TIMEOUT`，前端提示"首次加载较慢，请稍后重试"；后台继续建 |
| 10.5 | PG 不可用（batchId 查询） | 批次人数可能滞后 | 回退本地 `bi` 并标 `from:"fallback"` + 页面提示；**不报错**（列表还能看） |
| 10.6 | 深翻页（第 1000 页） | OFFSET 越大越慢 | 页码模式硬上限 `offset ≤ 20000`，超出返回 `code: OFFSET_TOO_DEEP` + 建议改用筛选；游标模式不受限 |
| 10.7 | 结果集过大（无筛选的全库） | 5 万条 | 硬上限 `total > 50000` 时仍只返回一页；排序/游标正常，**不要**一次返回全部 |
| 10.8 | 关键词特殊字符（`%`、`_`、引号） | 注入/匹配异常 | 全部走内存字符串匹配，**不拼 SQL**；正则转义后再用 |
| 10.9 | 全角/半角、简繁、空格 | 搜不到 | 统一归一化（§7 规则）；测试用例覆盖 |
| 10.10 | 用户快速连点"下一页" | 响应乱序 | `reqId` + AbortController，只认最后一次 |
| 10.11 | 两个标签页同时操作 | 数据互相覆盖 | 无共享状态；各自请求；写操作后各自刷新 |
| 10.12 | 删除客户后又恢复 | 列表/总数不一致 | 列表默认 `deleted=false`；恢复后由 15 秒指纹轮询触发刷新 |
| 10.13 | 客户 id 重复（数据脏） | 分页重复行 | 游标用 `(sort,id)` 去重；`byId` 以最后一次为准 |
| 10.14 | 服务端内存不足 | OOM / 卡顿 | 索引按需释放（10 分钟无查询释放 searchMap/sorted）；监控 `process.memoryUsage()` |
| 10.15 | 浏览器断网后恢复 | 一直转圈 | fetch 超时 8s + 上限 2 次自动重试 + 手动重试按钮 |
| 10.16 | 导出全部客户（需要全量） | 不能用分页 | 单独流式导出接口 `GET /points/export?…`（CSV 分块写，服务端流式，不进浏览器内存） |

## 11. 性能预算与验收

| 指标 | 目标 | 验收方式 |
|---|---|---|
| 列表首屏（50 条） | P95 < 300 ms | 本地压测 100 次取 P95 |
| 翻页 | P95 < 120 ms | 同上 |
| facets | P95 < 80 ms | 同上 |
| 单次响应体 | < 60 KB（50 条） | Content-Length |
| 服务端 RSS 增量 | < 80 MB | `process.memoryUsage().rss` |
| 浏览器堆 | < 150 MB | DevTools Memory |
| 结果一致性 | 100% | 与旧逻辑（全量内存筛）对拍 200 组随机条件 |

**对拍脚本**是硬性要求：改造前后各跑一次，同样的筛选条件，比较 id 列表与 `total`，**必须完全一致**。

## 12. 迁移与回滚

- 全程挂在开关后面：`localStorage['adm.serverPaging'] = '1'` 或 URL `?serverPaging=1`。
- 默认关闭 → 灰度到自己（你的账号本机）→ 稳定 3 天后默认开启。
- 回滚：关开关即可恢复旧路径（旧代码保留，不删）。
- `/mapPoints` **永不删除**，作为最终兜底。

## 13. 测试计划

### 13.1 接口级

- 空筛选 / 各单条件 / 组合条件；
- 排序 × 方向 × 游标翻到底；
- `batchId`（PG 可用 / 不可用）；
- `ids` 批量（0 / 1 / 3000 个）；
- 越界 page、offset 上限、size 上限；
- 中文/全角/编号/电话关键词；
- 缓存为空、预热中、文件损坏（人为改坏 `v`）。

### 13.2 前端级

- 首屏、翻页、跳页、筛选切换、搜索；
- 快速连点（竞态）、断网、超时、503 重试；
- 写操作后当前页刷新；
- 浏览器内存不随翻页增长（翻 200 页后堆大小稳定）。

### 13.3 故障注入

- 杀掉 server → 前端提示；
- 把 `map-points.json` 改名 → 走预热流程；
- 断开 PG（改 pgApiUrl 指向不存在端口）→ `from:fallback` 提示；
- 人为让索引构建 sleep 6s → INDEX_TIMEOUT 分支。

| 4 | 其余 C/D 类调用点迁移 + 清理死代码 | 0.5 天 | 中 |

**总计约 2 天**（不含你验收时间）。第 3 步是重点，差异必须清零才继续。

| 风险 | 概率 | 影响 | 缓解 |

## 17. 需要你确认的三点

1. **排序默认值**：列表默认按什么排？（现在是"最近更新"，改造后建议保持，可选"店名/建档时间/最后订单"）
2. **深翻页**：允许翻到第几页？我建议 offset ≤ 20000（约 400 页），更深的用筛选。
3. **灰度方式**：先只在你本机开（`?serverPaging=1`），稳定 3 天再默认开——同意吗？
