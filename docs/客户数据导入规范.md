## 一、核心口径（老板拍板，勿再搞错）

### 1. 只有两种客户，都是"我们的客户"

> 老板原话："**所有我给你表格中的客户，不管哪种形态，都是我们的客户，只是有的加入了商城，有的没有加入商城而已。**"

- ❌ **已作废**的说法：「新客户 / 老客户」、「潜在名单 / 待开发名单」、「商城主 vs 未匹配」
- ✅ **正确**的说法：**「已加入商城」** 与 **「未加入商城」** —— 都是我们的客户，**没有高低之分**
- 代码含义：一套集合装全部客户；「已加入商城」的事实来源 = **有 `mallKey`（系统Key）**
- ⚠️ **2026-09-23 判据统一（修正 004）**：**状态判据只认 `customerType`**（`'mall'` / `'new'`）；`mallKey` 降为**事实来源/关联键**。凡写 `mallKey` 处**必须同步推导** `customerType = mallKey ? 'mall' : 'new'`（两者永远一致）。**认领商城时也要补写 `customerType:'mall'`**（此前漏写 → 客户留在新客线，而后台已显示"已入商城"，同一客户两处说法不同）

### 2. 一套集合，不做旁路表

- **不要**建"平台店铺库 / 潜在客户池"这种旁路集合
- 平台画像（大众点评抓的信息）就是**客户档案的一个侧面**，直接挂在客户记录上
- 源表里出现的**每一行都是一个客户档案**

### 3. 同一个客户编号 = 同一家店（老板 / 老板娘各自注册）

> 有些客户在商城里有**两条档案、同一个客户编号** —— 这是**同一家店铺**，老板和老板娘各自注册的。
> **不是数据错误，不要当成重复脏数据删掉。**

**入库规则**：

| | 规则 |
|---|---|
| 数量 | 两条档案 → **视为一家** |
| 主副 | **购买次数多的为主，少的为副** |
| 客户详情页 | 信息展示**以主家为主**（副家信息作为补充/备用） |
| 销售订单 | **两家的订单 + 明细全都要**（合并计算、合并展示） |

**数据结构建议**：
```
主档案（购买次数多的那条）
  └─ subAccounts: [ 副档案的 _id / 系统Key / 客户名称 ]
     （或反向：副档案上打 mainAccountId 指回主档案）
订单表：两条档案的订单都关联到同一个"客户实体"（用主档案 _id 或统一的 customerKey）
```

#### 点评重复的处理规则（老板 2026-09-13 拍板）

> 老板原话："**点评上有重复的，就哪个信息更丰富就用哪个，差不多就用点评分数高的那个，一样的话就随机挑一个就行。**"

| 优先级 | 条件 | 取哪条 |
|---|---|---|
| 1 | 信息更丰富 | 取**有效字段多**的那条 |
| 2 | 丰富度差不多 | 取**点评评分高**的那条 |
| 3 | 评分也相同 / 都为空 | **随机挑一条** |

**"有效字段数"的定义**（脚本要按这个算）：遍历该行 45 列，剔除这些**不算有效**的值后计数：
`空值` / `'-'` / `'[]'` / `"['']"` / `False` / `0` / `'0.0'`

**本批实测案例（c53）**：
```
川东川菜馆(高镇商业区店)  有效字段 27/45  评分[空]  人均[空]   图片 1  收录 43191
红太阳川菜馆(高镇商业区店) 有效字段 27/45  评分[空]  人均 ¥44/人 图片 0  收录 43617
→ 丰富度打平 → 评分都为空 → 按规则落到「随机选一条」
```
⚠️ 但**两边各留着一半有用的信息**（红太阳有人均、川东有图片），随机选会丢一半。

#### ✅ 最终做法：方案 A · 字段级合并（老板 2026-09-13 拍板）

**不选一条，而是两条都读、逐字段合并。**

```
① 按上面三层规则先定出「主记录」（丰富度 → 评分 → 随机）
② 以主记录为基座，逐字段检查：
     · 主记录该字段【有值】  → 用主记录的（不覆盖）
     · 主记录该字段【为空】  → 用另一条记录的值补上
③ 【收录时间】例外 —— 两条都读，取【更早】的那个
     （例：川东 43191 vs 红太阳 43617 → 取 43191）
```

**c53 合并后的结果**：
```
人均消费 = ¥44/人        ← 来自红太阳（川东为空）
图片数量 = 1              ← 来自川东（红太阳为 0）
收录时间 = 43191（更早）  ← 特殊规则，取早的
菜品/营业时间/地址 = 取主记录那份
其余字段 = 谁有值用谁的
```

> 这样两边信息都不丢 —— 符合老板"**信息全进**"的总原则。

### 4. 坐标取数（分层优先级）

| 优先级 | 条件 | 用谁的坐标 |
|---|---|---|
| 1 | 有商城坐标 | **用商城侧**（`经纬度` 列，**实地验证过**） |
| 2 | 没商城坐标但有平台坐标 | **用大众点评的** `lng`/`lat` |
| 3 | 都没有 | `coord_status = 'pending'`，等业务员到店补标 |

> 注：商城侧 `经纬度` 列格式是 **`经度,纬度`**（如 `119.99912,28.917784`）；大众点评表是 `lat`/`lng` **独立两列**。
> 本批 463 家**全部走第 1 条**（商城坐标）；以后导入未匹配商城的客户走第 2 条。

### 5. 数据范围

- 当前**只导已匹配好的这一批（463 家）**
- 全市/全区总计约 8916 家（大众点评），其余未匹配的**以后再导**，届时走点评坐标

### 6. 信息全进，不做聚合

> 老板原话："**不要聚合，信息全进。**"

- 源表**每一列都要有归处**，字段级完整落库
- **不预存聚合字段**（如"常买品类 Top3"）；需要统计时**从明细表实时算**
- 订单和订单明细**全量入库**，不做汇总压缩

## 三、配对规则（shopuuid 硬匹配）

**新版商城表第 49 列 = 点评表内的 `shopuuid`** → **一一对应，不用模糊匹配**。

```
① shopuuid 直接对齐                     → 实测 462/463（99.8%）
② 剩余的（1 家）用 店名/电话/坐标 兜底    → 或人工确认
③ 客户编码（客户名称前缀 c402 / a181）    → 用于关联订单
```

**为什么 shopuuid 比店名匹配强**（实测例子）：
```
商城：d141 兰州拉面   →  shopuuid k4XFECgsNYirdInT  →  点评：兰州牛肉拉面 ✓
店名完全不同，模糊匹配必失败，shopuuid 一枪命中。
```

**归一化辅助规则**（兜底时才用）：
- 去客户名称的编码前缀（`c1050 ` / `a71 `）
- 去括号内容、只留中英数、转小写
- 电话：拆分主号/备号，正则 `1[3-9]\d{9}`

## 五、导入方案（防 -601008 超时）

云函数单次执行有超时限制，**大导入必须前端分片 + 断点续跑**（沿用项目已验证的做法，见 `wipeData`）。

```
① 建/校验集合（init 云函数 —— COLLECTIONS 必须补上 order_items）
② 先在浏览器把 463 行合并成 460 家（同编号 → mainAccountId / subAccounts）← 2026-09-23 提到 customers 之前
③ customers   分片上传   ⚠️ 按字节切（≈30 行/片）
④ orders      分片上传   ⚠️ 按字节切（≈70 单/片，顺手写对 orders.customerId）
⑤ order_items 分片上传   ⚠️ 按字节切（≈170 行/片）
```

> 🔴 **2026-09-23 变更（修正 010，**推翻**本节原来的"按条数"三档）**：原写 `customers 60 家/片 / orders 200 单/片 / order_items 300 行/片` —— **全部作废**。
> 实测单行体积：customers 平均 **2371 B**（最大 **6200 B**）、orders **1026 B**、order_items **441 B** → 按上面三档切分别约 **142 / 205 / 132 KB**，**都超过云函数 100KB 出入参上限**；而且最大行 6200 B 时 **13 行就可能到 80KB**，按条数切也不安全。
> ✅ **正确做法：按字节切片** —— 累加 `Buffer.byteLength` 到 **60~70 KB** 就切一片（给外层包封留余量）。

**平台侧/商城侧合并规则**：**字段级取优**（不是整条覆盖）——
商城字段从②来、平台画像从①来、各填各的空位；**冲突时以商城为准**（我们自己的系统数据）。

## 八、重要提醒（踩过的坑）

1. **不要用"像不像人名"去质疑数据** —— `业务负责人` 列原值就是 `快餐盒c聚火配送🔥` 这种，**值是什么填什么**；`签约业务员` 同样取原值
2. **不要写「范宇琨」** —— 那是开发者（手机号 13067737286）的测试账号
3. **坐标顺序**：商城表 `经纬度` 是 `经度,纬度`；点评表是 `lat`/`lng` 两列
4. **日期格式**：商城表的「添加时间/最后下单」是 `2026-03-28 17:14:30.497000`（带微秒）；订单的「下单时间」是 **Excel 序列号**（如 `46273.52932369213`），要做转换
5. **订单金额**：`订单金额`/`实际金额`/`缺货金额` 都是浮点字符串（`145.0`）
6. **Excel 数字列**：电话、金额等数字列读出来可能是 `float`，要转字符串并去掉 `.0`
7. **大众点评的 `phone1` 常是 `-`**（没电话）→ 不能假设它一定有值
8. **商城坐标 vs 点评坐标偏差**：本批 463 家中位数只差 **12 米**（说明实地验证的坐标准），但有 **26 家偏差 > 200 米**，最大的 15 公里（`c887 贵州兴仁大山地摊火锅` 15240 米、`c752 水城羊肉粉店` 13533 米）→ 大概率某一边标错了，建议抽查。**按口径仍用商城坐标**。
