# 商城配对确认 · 口径与实测（2026-10-11）

> **老板 2026-10-11 定：导入商城表的意义变了** —— 现在导入的商城客户，**系统内一定有对应的客户**
> （= 系统里已有的这家店"**加入了商城**"），而不是"从商城表新建一批陌生客户"。
> 因此需要一个**人来过一眼**的「商城配对确认」界面。
>
> · 演示稿：`_scratch/商城配对确认-演示.html`（四块：电话相同 / 电话不同 / 三个电话 / 商圈建议）
> · 本文是**口径 + 实测**的唯一依据；与旧文档冲突时**以本文为准**
> · 状态：**口径已定，真后台尚未改动**（等老板看完演示稿点头）

## 一、配对判定（按重要度 · 老板定）

| 序 | 依据 | 说明 |
|---|---|---|
| ① | **店名相同** | 第一重要。老板："现在我尽量让店名相同，这当然是第一重要信息" |
| ② | **电话相同** | 第二重要。**一旦相同就是"铁证"** —— 界面上必须**单独用绿标标出**，别埋在分数里<br>老板："确实会发生没有填写和不相同的情况，但是一旦相同就是铁证" |
| ③ | **地址** | 第三重要，且**分两部分**：**区域**（`region`，如"浙江省>金华市>永康市"）+ **填写地址**（`address`） |

---

## 二、合并口径（老板定）

| 字段 | 取谁 | 备注 |
|---|---|---|
| 店名 / 电话 / 地址 / 地区 | **商城优先** | 商城有值就覆盖系统的 |
| **经纬度 / 商圈** | **一律用系统内的** | 因为**商城表不附带经纬度** |
| 标记 | `customerType='mall'` + `mallPending=false` | 代表「已加入商城」 |

⚠️ **坐标绝不覆盖** —— 沿用 2026-09-29 定的 `MALL_NO_TOUCH`（现场采的坐标优先）。

## 三、电话怎么排（老板定）

| 情况 | 做法 |
|---|---|
| 两边**相同** | **只留一个** |
| 两边都有但**不同** | 按 **`1`（商城）· `2`（系统）** 放置，**两个都留着** |
| 加起来**三个不同** | **只保留「商城的 + 系统的第一个」**，第 3 个**丢弃** |

## 四、商圈两边都空 → 按坐标算建议（老板定）

- **范围：先 200 米；参考值太少再放 500 米。**
  ⚠️ **不要一上来就 1 公里** —— 老板："一公里就会出现，远的地方占大多数之后，就会**挤占附近的权重**了"。
- **算法**：取范围内**已有商圈信息**的店 → 按**商圈名**计数 → **最多的那个**作为建议值。
- ⚠️ **「永康市」这类"市名"照用、不排除** —— 老板："这里'永康市'也被定成了商圈名称，
  没办法，**上一个信息录入员就是这么弄的，我们也只好将错就错了**"。
- 老板确认后可**改**、可**手动填**，也可**留空**。

## 五、交互（老板定）

- **全部都要老板确认** —— ⚠️ **不保留"≥75 分自动配掉"的老逻辑**；高分只是**默认预勾**。
- 一行 = 一个商城客户；右边列出**系统内候选**（按像的程度从高到低，**带匹配理由**）。
- **系统里没找到的** → 单独一组；**那一组里可以直接新建客户**（按商城这条建档 + 直接标"已加入商城"）。
- 左边商城那条 / 右边系统候选，**关键信息并排**（店名 / 电话 / 地址 / 编号），一眼能判对错。

## 七、踩过的坑（下次别犯）

1. ⚠️ **查"系统里有没有这家店"，别只查 `source='field'`** ——
   老板 xls 里的「安顺屯滋味」在库里 **`source` 是空的**，我第一次只查 field 就**漏了它**
   （老板："系统内有的，我看到了的"）。
   ✅ **正确做法**：**按店名 / 电话直接查**，别预设 `source`。
2. ⚠️ **服务器 psql 的中文是 GBK，会乱码** ——
   查中文店名可用 **Unicode 转义**（`name LIKE U&'%\5C6F\6ECB\5473%'` = 屯滋味）；
   **用电话查（纯数字）最省事**，不受编码影响。
3. ⚠️ **别拿"地名"当关键词** —— 我第一次用"安顺"查，出来 **72 家**（那是**贵州的地名**）；
   应该用**店名的特征词**（"屯滋味"）。
