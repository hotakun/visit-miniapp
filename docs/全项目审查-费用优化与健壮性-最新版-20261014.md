# 聚火拜访全项目审查：费用优化、代码质量与健壮性

> 最新版 / 第二版，2026-10-14。基线：`e481e89f80d62b7d1335ecbd522c9e01d59b7865`。本轮只审查与写报告，不修改业务代码、客户资料、版本号或线上数据，不执行部署、迁移和生产请求。旧报告保留，本报告取代旧报告中针对“当前实现”的判断。

## 1. 结论先行

**当前实现已明显减少重复读取，但尚不能判定完整业务流程可靠。优先事项不是继续拉长轮询或缓存期限，而是补齐身份校验、会话幂等、异步响应归属和同步发布协议。**

最值得先处理的风险：

| 优先级 | 问题 | 可能表现 |
|---|---|---|
| P0 | 老板注册信任客户端手机号，未关联服务端手机号验证 | 未绑定微信可获得或重绑特权身份 |
| P1 | 强行离页自动提交与云端结果、超时校验冲突 | 页面说已自动保存，实际上成果未提交，媒体未保住 |
| P1 | 最后一段录音尚未转存、入列，提交已继续 | 文字结果成功，最后一段录音却缺失 |
| P1 | 拜访升级查询缺人员、任务归属；提交和定时收尾非原子 | 两个人同店串记录，弱网重试重复，定时器覆盖人工成果 |
| P1 | 地图常驻 `_loaded` 绕过缓存失效；旧媒体回包覆盖新详情 | 打勾、重排没变化；新记录出现后又消失 |
| P1 | 客户分页按 ID 排序，却在每页推进时间水位 | 服务器永久漏掉部分客户变动 |
| P1 | 同步前确认信号、清表后全量重建、错误被变成空成功页 | 数据静默滞后、空表或半表被当成最新完整数据 |
| P1 | 后台归档分支遗漏释放 `autoBusy` | 轮询无报错地一直停止 |

**证据口径：**P0 表示应立即评估并封闭的特权边界，不等于已发生攻击；P1 表示高优先级正确性、数据保全或访问控制问题；P2 表示成本、边界或维护性改进。本文的严重性根据可触发后果判断，不根据问题数量判断。

## 4. 身份与权限边界

### S01 / P0 / 确定：老板注册用输入手机号决定特权身份

**证据：**[login:235-270](../miniprogram/cloudfunctions/login/index.js#L235-L270)、[login:343-351](../miniprogram/cloudfunctions/login/index.js#L343-L351)。注册读 `e.phone`；号码匹配老板通道后，更新已有账号的 OPENID、姓名、角色和启用状态。独立的 `verifyPhone` 只返回号码，未建立服务端验证凭据；`phoneVerified` 也来自客户端。

**触发与影响：**未绑定微信的请求携带该号码即可进入特权分支，已有绑定还会被覆盖。内存数据库桩已复现重绑，不代表已探测线上可达性。前端按钮是否要求验证不能替代服务端授权。

**建议：**老板通道必须在同一服务端操作中消费微信手机号凭证并比对；已绑定账号不得自动覆盖。换绑走明确审批、一次性凭证和审计记录。先封闭特权入口，再研究体验。

**验收：**伪造手机号和验证标志均零特权写入；合法老板首次验证成功；他人不能覆盖已有绑定；正常业务员注册仍进入审核。生产账号不要作为测试样本。

### S02 / P1 / 确定缺口、部署条件：定时与初始化入口不能靠请求外形认证

**证据：**[adminapi:619-634](../miniprogram/cloudfunctions/adminapi/index.js#L619-L634) 在管理员鉴权前以 `Type/TriggerName` 判断定时调用；[transcribe:130-142](../miniprogram/cloudfunctions/transcribe/index.js#L130-L142) 把无 OPENID 的 poll 当全局定时调用。分项审查另见 `init/index.js:40-97`、`seed/index.js:20-96` 无普通身份鉴权，`bindadmin/index.js:6,11-28` 用静态开通码。

**影响：**普通调用若可达，匹配定时字段可触发过期扫描和自动写入；初始化/种子可写业务库。无 OPENID 不等于平台定时器。未确认这些函数是否在生产开放，不能宣称公网已可利用。

**建议与验收：**核查平台实际调用权限及可信来源字段，不自行猜 API；必要时拆出只允许运维/定时调用的函数。生产关闭种子入口，开通凭证短期、一次性、原子消费。模拟定时字段的普通请求应被拒，真实定时器仍执行，未授权 init/seed 零写入。报告不披露静态开通码或账号初始秘密。

### S03 / P1 / 确定：停用与游客只读防护不一致

**证据：**`visits/index.js:63-97`、`tasks/index.js:70-109`、`transcribe/index.js:145-176` 按 OPENID 或 trialId 认人，但不统一检查 active；`visits.start/saveDraft` 缺游客拦截；`tasks` 建店、改自建店和照片写入的部分路径缺游客拦截。`saveCustPhoto:828-829` 仅删除分支拦游客，新增分支 `843-851` 没有同样保护。坐标主路 `coordfix/index.js:57-105` 也没有游客拦截，field 分支才有。

**影响：**客户端已登录不代表账号仍启用；保留 OPENID 的停用账号直接调用可继续业务动作。游客入口隐藏写按钮不能阻止直接调用。

**建议：**每个云函数身份解析后统一校验 active、库内角色、模式和写权限；保留合法 `alsoSalesman` 降权，游客只读明确列 action。不能把老板演示假成功与真实写成功混淆。

**验收：**按“未登录/停用/游客/业务员/老板/老板兼业务员”直调所有写 action；拒绝时数据库、云存储删除、ASR 均无副作用。

### S04 / P1 / 确定：指定转写 ID 可越过归属，终态会被超时逻辑改坏

**证据：**[transcribe:280-296](../miniprogram/cloudfunctions/transcribe/index.js#L280-L296) 指定 transcriptIds 或 visitId 时未加本人条件；[settleOne:317-324](../miniprogram/cloudfunctions/transcribe/index.js#L317-L324) 先按 requestedAt 判断超时，没有先拒绝修改完成态。

**影响：**知道他人记录 ID 的业务员可读文本或驱动更新；显式查询超过 30 分钟的 done 记录，会把状态改成 failed。后者已在内存桩复现。

**建议与验收：**查询和返回两次都附加授权范围；settle 只处理 processing/pending，完成态幂等返回。A 查询 B 的记录必须拒绝，done 在反复查询及跨小时后保持 done。

### S05 / P1 / 条件风险：本地后台 HTTP 并非天然私有

**证据：**[server:975-984](../admin/server.js#L975-L984) 静态目录映射整个 admin 目录，使用字符串 startsWith 判断边界；`server.js:1135` 监听不指定 loopback。本地缓存 patch 和服务器代理部分路由没有统一会话认证，见 `618-625,860-870`。PG 状态页另用源码中的简单口令，需独立评估。

**影响：**若 LAN 端口被放行，可能读配置、缓存或调用本地写接口；即使仅本机，也应防跨站请求和误读非静态文件。**未验证防火墙、公网暴露或实际泄露。**

**建议与验收：**只需本机时明确绑定 `127.0.0.1`，静态文件白名单，目录边界用路径语义而非前缀；本地写接口检查会话/Origin，设请求体大小及超时。测试配置、日志、备份路径不可读取，未认证写被拒，LAN 不可连接；PG API/监控不在 URL 暴露长期秘密，并核查实际 TLS。

## 5. 拜访、媒体和成果保全

### V01 / P1 / 确定：强行离页自动保存承诺没有闭合

**证据：**[visit.onUnload:344-380](../miniprogram/miniprogram/pages/visit/visit.js#L344-L380) 有内容即调用 submit，固定 `skipLoc:true`，允许空结果，未上传或传 photos/audios，业务失败 `ok:false` 也不处理，随后清 `_startKey`。云端 `visits/index.js:456-458,501-511` 必须有合法结果，skipLoc 必须已经超时且有草稿结果。`saveDraftNow:326-328` 无 taskId 直接返回。

**触发与影响：**开始几分钟后输入文字/拍照/录音再强行离开，自动请求会被拒；自由拜访连草稿都没上报。关闭页面后仅结果草稿也保不住现场媒体。已复现客户端错误请求形状。游客判断函数名与公共模块导出一致，未将函数名列为问题。

**建议：**把“离页保存草稿”和“最终提交”分清，持久化完整本机 outbox，包括客户/会话/身份和本机媒体路径；下次启动可恢复。离页不能用未到期的 skipLoc 冒充最终提交。服务端是否允许无结果草稿应单独设计，不放宽正式提交的现场校验。

**验收：**任务与自由拜访分别测仅文字、仅照片、仅录音、无结果、强制杀进程、无网络；未完成成果可恢复，界面明确待提交，空内容才取消，编辑/游客不误写。

### V02 / P1 / 确定：最后录音尚未入列，提交就开始了

**证据：**[visit:503-521](../miniprogram/miniprogram/pages/visit/visit.js#L503-L521) onRecDone 最前面 resolve `_recStopResolve`，随后才 await 转存和加入 recs；`confirmSubmit:843-850` 只等该 resolve 就检查证据。

**影响：**录音中直接点确认，只有这段录音且转存较慢时，提交 audios 为零。已有段时也可能漏最后一段。内存桩通过延迟 getUploadPath 已复现。

**建议与验收：**stop 等待“文件转存完成并已加入列表”的 Promise，不等单纯 onStop；失败须反馈、保留草稿，录音错误/中断要结束等待，不能无限挂起。测试直接确认、慢转存、录音权限拒绝、保存空间满，照片/录音条数与云端一致。

### V03 / P1 / 确定：升级 ongoing 没有绑定本人和任务

**证据：**[visits:549-555](../miniprogram/cloudfunctions/visits/index.js#L549-L555) 仅按 customerId、当天、ongoing 查第一条，然后覆盖为当前人/当前任务的提交。`start:242-243` 同样只判断客户当天已有 ongoing，直接返回 ok。

**影响：**A 在客户 C 拜访，B 自由拜访 C 后提交，可能把 A 的记录变为 B，连 taskId、证据及人员归属一起改。任务权限校验存在，但保护不了不带任务的旁路。

**建议与验收：**start 返回服务端 visitId，后续草稿、submit/cancel 均绑定本人、客户、任务、会话和状态；已有他人 ongoing 不得假作本人开始成功。双人同店、同人跨任务用例必须互不覆盖。

### V04 / P1 / 条件风险：正常提交、取消和定时器缺统一原子状态机

**证据：**`visits.start:214-249`、`submit:549-555` 为先读后写；没有持久化请求幂等键。`adminapi.visitTimeoutTick:1265-1295` 用旧 ongoing 快照，之后直接按 doc ID 更新/删除，未限定仍为 ongoing。正常 submit 写成果后 `visits:588-589` 的客户 reviewFlag 更新仍可抛错。

**影响：**并发 start 可突破单开；已保存但响应丢失后重试，可能新建第二条。定时器先读、人工随后提交，定时器可能覆盖或删除已完成记录。主成果成功、附属标记失败，仍可能向客户端报失败，不能只修手机收尾。

**建议：**每次真实拜访一个会话，每次提交一个操作 ID；条件更新/事务竞争 ongoing→终态，校验命中数；重复操作返回原结果。附属统计、标记、通知作为可重试工作，不让已提交变成未知失败。**允许真实二次回访，不得用客户＋日期唯一键误禁止它。**

**验收：**并发 start、提交后断响应、取消与提交交错、定时器与人工交错、附属更新失败，最终恰一份该会话成果，真实第二次会话仍可新增。

### V05 / P1 / 确定：照片写失败仍回成功，删除还可能先破坏文件

**证据：**[tasks.saveCustPhoto:836-851](../miniprogram/cloudfunctions/tasks/index.js#L836-L851) 客户 update 的异常被 silentCatch 吞掉，继续删云文件或返回“已保存”。

**影响：**数据库没删照片引用，云文件却删掉，产生坏引用；新增没有写入仍提示保存成功。这不是客户端没刷新能补救的问题。

**建议与验收：**关键业务 update 必须传播失败；成功提交引用变更后再做可重试文件清理，先核验无其他引用。注入 DB update 失败，应返回失败且旧文件可用；文件清理失败不回退业务成果，但有待清理记录。

### V06 / P1 / 确定：任务结束的收尾承诺与服务端限制冲突

**证据：**`adminapi.finishTask:6048-6068` 明确保留在途并允许提交，但写 status=done；`visits.submit:443-445` 对 done 一律拒绝。deadline 仅限制 published，reviewing 的越期行为需统一；改期/延期 `adminapi:1955-1984` 没有 archivedAt 限制和统一版本写入。

**建议：**定义 published/reviewing/done/archived 与 deadline 的单一状态规则；只给“结束前已开始”的合法会话受控收尾，不开放任意新拜访。归档恢复必须独立授权，不靠普通延期隐式复活。

**验收：**截止日零点前后、后台提前结束、在途提交、归档任务延期、reviewing 越期按矩阵一致。

### V07 / P1 / 静态缺口：软删除与编辑旁路没有统一约束

**证据：**`adminapi.createTask:1803-1859` 未逐个检查客户存在/未删除；`visits.start:179-259` 不检查目标客户，submit `451-453` 仅检查存在；编辑 `614-636` 未复用结果枚举、配置照片上限、录音时长及强制证据校验。

**影响：**旧选择快照可能派入回收站客户，已删客户仍能从旧页自由拜访；直接编辑可绕过正式提交限制。任务和客户变更还须处理并发。

## 6. 缓存、请求生命周期与界面一致性

### C01 / P1 / 确定：缓存 uid 取写入时身份，不是请求时身份

**证据：**`detailCache:20-49`、`mapCache:16-38` 写入时取 globalData 当前 user；首页 `571-593,619-646` 等回包不校验会话 epoch。同 uid 老板/业务员模式的部分详情键也未区分。

**影响：**A 请求在途→切 B→A 回包按 B 入键；已经有 uid 的键仍不能防此竞态。内存桩已复现错误归档，但未证明线上每次切身份都发生。

**建议与验收：**请求开始固定 uid/mode/session epoch；响应归属不匹配即丢弃，缓存使用固定上下文。延迟 A 回包后切 B，再放行，B 页面和缓存不得进入 A 数据。

### C02 / P1 / 确定：地图 `_loaded` 绕过存储缓存失效与过期

**证据：**`map.onShow:39-49` 只在未 loaded 时 load；load 成功/命中缓存置 true。`visit:917-920` 只删除存储缓存，不清常驻页面内存。重排 `map:383-385` 只清 loaded，没有删除缓存或设 force，loadTask 又能命中旧路线。

**影响：**提交、跨天、后台改任务或存储 TTL 到期都可能不刷新常驻地图；重排显示成功但恢复旧路线。onShow 不再校验已在桩复现。

**建议与验收：**存储和内存统一失效 revision；onShow 校验身份/日期/任务 revision，不必每次全量请求。重排先失效后 force，保留所选天和用户视野。测提交打勾、重排、跨零点、切模式和撤回任务。

### C03 / P1 / 确定：旧媒体回包能让新详情回退

**证据：**`customer:398-407` 并行媒体更新和静默详情；`_refreshMediaUrls:522-541` 把启动时的旧 res 整块写缓存/重渲染。静默新详情 `504-507` 又沿用旧 URL，没有按新增 fileID 补齐。

**影响：**新记录先到，旧媒体后到，记录再次消失，旧缓存被赋新时间；新录音可能没有可播放 URL。旧媒体覆盖新版数据已桩复现。

**建议与验收：**业务数据与 URL 映射分开；媒体只按 fileID 合并到当前版本，不带旧 res 回写，校验 epoch。新增 ID 必须补 URL；保存折叠状态。分别强制两种返回顺序，当前记录不可回退，媒体和档案版本一致。

### C04 / P1 / 确定：辅助客户对象仍继承上一家的字段

**证据：**`customer:381-384` freeVisit 入口 Object.assign 旧对象，仅换 id/清 taskId；`1186-1195` 再次合并，freeTripId 未清，坐标/地址用旧值兜底。新店列表入口仅带 freeVisit，没有明确卡归属。

### C05 / P2 / 确定：失效标记和静默更新缺确认语义

**建议与验收：**前台/page epoch＋in-flight 单飞；旧回包不续排。收到版本变动统一标脏而非只通知当前页，必须读新数据的场景 force。延迟请求后隐藏/卸载再回包，timer 不复活，快速前后台切换仅一个循环；双身份的 ver/reviewStatus 与当前模式一致。

## 7. 后台与 PG 同步正确性

### D01 / P1 / 确定：ID分页与每页时间水位组合会漏数据

**证据：**`adminapi.custSync:2684-2688,2731` 固定 since＋ID cursor；`pgsync.round:236-254` 不传 cursor，每页将 since=maxU。

**影响：**第一页含新时间戳，ID较大的较旧更新/同毫秒记录在第二页被过滤。内存样本1500条，前1000条时间10000、后500条时间100，实际只写1000条并推进到10000。后续增量兜底仍用错误水位，不自动补回。

**建议与验收：**本轮固定 since，完整消费 next，全部成功后提交水位；进一步用 `(updatedAt,id)` 或可靠revision，并考虑同步期间同ID再次修改。2500条逆序/同时间、任意页失败、同步期间更新，逐ID无遗漏。

### D02 / P1 / 确定：信号先发、先确认，失败后可能不再重试

**证据：**`adminapi.createTask:1802` 等在写前 touch；`touch*:1372-1422` 是3秒前沿节流，没有尾沿。`pgsync:224-234` 同步前赋 lastHandled 和 lastBusyRun；`store.checkDirtyFromPg:347-355` 拉成功前赋 lastDirtyAt。改期/延期 `adminapi:1955-1984` 缺 taskDirty/updatedAt 更新。

**影响：**消费者见信号时最终写入未完成；失败却确认，下一轮“无变化”跳过。日志“下轮再试”不总成立。单表1小时兜底也可能被整轮2小时跳过拦住；持续其他活动可推迟兜底。

**建议：**写成功后发单调 revision，必要时可靠事件；每表同步成功才确认该表，失败表独立重试；兜底到期独立于整轮门槛。信号用于通知，不作已经同步成功的凭据。

**验收：**暂停数据写/让同步失败且信号保持不变，下一轮仍补齐；3秒内连续写不漏尾部；改期、结束、删除、恢复全部覆盖信号契约。

### D03 / P1 / 确定：全量清表和空成功页会发布不完整副本

**证据：**`pgsync:369-405,441-481,504-540,544-562` 下载前 DELETE，未使用整体事务/代际切换；`adminapi.exportBatchMembers:6083-6091`、其他导出 `6106-6157` 查询失败可转换成空页 ok:true。visits 60页上限耗尽仍写成功水位。

**影响：**读API可见空/半表；异常被当正常结束，下一轮可能又跳过。源码是确定的发布缺口，实际数据规模和异常频率未知。

**建议与验收：**staging/generation 全量构建，明确complete/count/checksum，通过后短事务切换；错误不是空数据，上限耗尽返回截断/续跑而非完成。逐页注入失败、读取与重建并发，API只见完整旧版或新版。

### D04 / P1 / 确定：删除、恢复与水位不是完整事件流

**证据：**`adminapi.pollDirty:1444-1456` 仅近7天、1000条、无分页；`pgsync:142-150` 永久墓碑；`pgapi:/sync:185-187` rows不排除deleted，墓碑不按tbl过滤；`/stat:191` 只取客户最大updated_at；`/newshops:299-302` 永久排除deleted_ids中ID。

**影响：**纯删除未推动更新时间，客户端可能不拉；大批删除/停机跨窗口会漏名单；删除行既在rows又在removed时合并可能再追加；恢复客户仍被历史墓碑排除在新店列表。共享墓碑表还应防跨表ID干扰。

**建议与验收：**delete/restore事件带表、操作类型和版本，分页并确认消费；活行与墓碑语义互斥，恢复清除/超越旧墓碑；状态revision包含纯删除。1001条删除、停机超过7天、删→恢复→再删、纯删除必须端到端对账。

### D05 / P1 / 确定：缓存 patch 丢水位，异步同步能覆盖本地已确认变更

**影响：**本机时间领先时漏未同步变动；下载期间操作patch，结束时旧快照覆盖刚改字段/新增/删除。tmp→rename防半文件，但不能防逻辑陈旧覆盖。

**建议与验收：**保留服务端水位，单写队列或版本CAS；合并重读当前代际，对本地待确认操作进行有序重放，副本不反向成为客户真相源。暂停下载→patch→恢复、模拟时钟偏差和并发删除，成果不得回退。

### D06 / P1 / 确定：轻status没有保鲜闭环，归档分支可锁死轮询

**证据：**server `/mapPoints` 才触发checkDirtyFromPg，status不触发，见 `839-842,908-921`；`admin.html:8847-8850` 只比较count。同数量更名/改坐标不重绘，count=0直接return。`autoTick:6300` 提前return绕过 `6323` 释放autoBusy，已桩复现。

## 8. 笔记、GPS与辅助流程

### A01 / P1 / 确定：笔记文件和索引不具一致提交

**证据：**`notes.remove:79-84` 先删文件，忽略write失败并返回true；编辑器 `delPhoto:223,delRec:290` 保存前直接删已引用文件；拷贝失败 `207,268` 回退临时路径仍可保存。全局notes_v1和目录没有用户隔离。

**影响：**本机存储满时“删除成功”但索引仍在、照片已坏；编辑后没保存就退出，旧笔记媒体已经消失；临时路径可在重启后失效。删除失败行为已复现。跨用户共享是否符合老板口径需确认，不能直接删除或迁移既有记事。

**建议与验收：**元数据先成功提交，文件延后清理；编辑只记录待删，保存前不破坏原稿；持久化失败明确报错，不保存临时路径。说明共享/个人口径后才做uid隔离及无损迁移。满空间、未保存退出、重启、切身份均无假成功或旧稿破坏。

### A02 / P2 / 确定：本地记事转写等待期与服务端任务不一致

**证据：**`notes/editor:325-342` 每4秒轮询12次，约48秒就失败；注释和UI说1~3分钟，云端30分钟兜底。finally即删音频，transcriptId未存入本机笔记，任务未完成或退出页面也会走清理。

**影响：**可恢复的处理中被显示失败，服务端可能仍取音频，删除能否影响ASR取决于其已下载时机；重试可能再次上传和收费，后续结果无本机恢复入口。

**建议与验收：**持久化任务ID和状态，48秒只能表示“仍在处理”，按完成/最终失败清理临时云文件，退避轮询且可下次恢复；明确本机笔记只在主动转文字时上云。用2分钟结果、退出重进、零字成功和删除失败测试。

### A03 / P2 / 确定：GPS失败不复位，异步连接及全局事件缺会话边界

**证据：**`capture.start:83-85` active直接return；`_fail:209-212` 不清active；页面onError置capOn=false后复用同实例。`start/_onFound` await后未校验代次；`ble:43-50,195` 全局事件未过滤deviceId/特征。capture `359-365` 未透传estimate中的se/nEff/halfDiff，而getResult `151-154` 读取这些字段。

**影响：**扫描超时后点重试可能什么也不做，已桩复现；停止/退出时迟到连接继续订阅；其他设备断连可能改变本设备状态。诊断精度字段缺失，不能据此宣称“接收机精度不合格”。

**建议与验收：**失败清理资源并允许重启，连接流程使用epoch，事件按设备/服务/特征过滤；getResult精度契约对账。授权拒绝→重试、扫描超时→重试、连接中停止、双BLE设备、断连重连均测试。不要擅改已有实测通过的滤波阈值和接收机配置。

### A04 / P2 / 待硬件核验：GPS“收敛”不等于绝对准确

NMEA无校验和被 `nmea:6` 放行，坐标分钟/范围未严格限定；应明确是否为真实设备必需兼容。StaticFix已有稳健权重、600样本上限、连续驻留和有限值防护，不建议无依据重写；capture使用GGA卫星数进入质量门，再用GSA展示真实数，两者口径应说明。

建议录制已授权的原始帧，在隔离区回放截断、坏校验、缺校验、断流及移动样本；用独立基准点评估偏差，不能只用rms低证明店门口绝对位置正确。本轮未做硬件精度试验。

## 10. 代码质量改进原则

1. **统一成功语义。**关键写失败必须失败；附属失败单独记录；响应丢失表示“结果待确认”，不是“肯定未写”。对已成功成果的收尾不能重新提示提交失败。
2. **把核心边界做深，别直接拆成几十个小文件。**优先集中身份/写权限、会话终结、关键写结果、分页完成和缓存失效契约；模块重构在行为测试齐全后做。
3. **减少双份清单。**商城规范化、客户字段PG映射、页面newshop/custedit重复规则、缓存可见性都须对账。体检目前能检查“白名单action存在”，不能自动证明所有新写action都被列入，需反向权限/失效契约。
4. **错误分级而非全静默。**静默仅适合已有安全快照的辅助更新；首次加载、关键写、同步不完整应明确可观测，不把0、空和失败混为一谈。日志只记操作ID/阶段/数量，不记口令、完整电话或原始录音。
5. **所有页数上限有完成标志。**到上限且hasMore仍真不算成功；所有游标含稳定排序及固定过滤范围。分项审查的adminapi.fetchAll第二页覆盖原_id条件（约1131行）也需补范围AND与测试。
6. **时间与版本各司其职。**数据updatedAt、核验verifiedAt、同步cursor、本机syncedAt、通知revision不能互相充当。用户日期与业务截止时间统一东八区，常驻页面显式处理跨日。
7. **建立行为测试而不只加语法检查。**测试应该在故障发生前阻止它，而不是绿灯后由老板肉眼发现。没有必要为了本文立即安装新框架，现有Node内存桩即可起步。
