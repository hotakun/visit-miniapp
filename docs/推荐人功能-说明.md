# 推荐人功能 · 说明（2026-09-24 老板拍板，**已开发完成、待部署**）

> 一句话：**谁分享的链接把人拉进来，就记谁为推荐人**；存量的人当年没有分享链路，**后台手工补录**。
> 本文是权威口径说明；代码落点在 app.js / utils/share.js / 9 个页面 / login 云函数 / adminapi / admin.html。

## ⚠️ 边界（2026-09-24 老板专门澄清过，别再搞错）

**推荐人是"员工 ↔ 员工"的关系**：业务员 / 管理员 / 老板**互相之间**的推荐，**跟客户没有任何关系**。

- 推荐人**只能从系统内的人里选**（`users` 表），客户表 `customers` **全程不参与**
- **客户不会算进员工管理** —— 人员管理里出现的永远只有员工
- 唯一提到"客户"的是一个**统计数字**：推荐排行里的「带来入商城客户」＝ **被推荐人**（员工）谈成了多少家，
  数据源是**拜访记录**（`visits.result`），**不是**把客户挂到员工名下；它是衡量"你拉来的人干得怎么样"，不是客户归属

## 一、老板拍板的三个口径

| # | 口径 | 说明 |
|---|---|---|
| 1 | **存量怎么处理** | **链接自动带 ＋ 后台手工补录**（两者都要） |
| 2 | **谁能当推荐人** | **只能是系统内的人**（业务员 / 管理员 / 老板都能被选）；存 `_id` ＋ 姓名快照 |
| 3 | **用途** | 不只是记录，**还要统计**（拉人排行 / 转化） |

## 二、数据结构（新增字段）

```js
// users（业务员 / 管理员都适用）
referrerId: '',        // 推荐人的 users._id
referrerName: '',      // 姓名**快照**（防对方改名/离职后显示空）
referrerSource: 'link' | 'manual',   // 来源：🔗 分享链接自动带 / ✏️ 后台手工补录
referrerAt: 0,

// registrations（待审核申请）
refFrom: '', refFromName: '', refAt: 0,   // 谁分享的链接拉来的
```

## 三、链路（4 段）

1. **分享** —— 9 个页面的 `onShareAppMessage` 统一走 `utils/share.js`：
   `path = /pages/login/login?ref=<分享者 users._id>`
   （未登录时分享**不带** ref；指向登录页 —— 未登录的人打开就看到注册表单，已登录的人会被 login 页 `onShow` 自动送进首页）
2. **接收** —— `app.js` 的 `captureRef()`：`onLaunch`（冷启动）**与** `onShow`（热启动）两处都接 →
   存 `globalData.refFrom` **＋ storage 持久化**（防"点链接进来但当时没注册，之后再打开就丢了"）
3. **提交** —— `pages/login/login.js` 的 `submitReg()` 带上 `ref` →
   `login/register()` **校验该 id 真实存在**（防伪造；查不到就**静默忽略**，绝不阻断注册）→ 写 `registrations.refFrom/refFromName`
4. **落库** —— 后台审核通过（`adminapi.reviewRegistration`）→ 写 `users.referrerId/referrerName/referrerSource='link'`
   **兜底**：本次申请没带 `refFrom`（被拒后重提会**新建**一条申请）→ 回查同 `openid` 的历史申请里最近一条带 refFrom 的

## 五、统计口径（⚠️ 别混）

| 指标 | 口径 |
|---|---|
| **拉人数** | `users` 里 `referrerId = 我` 的**已入职**人数（待审核的单独一列） |
| **下级拜访数** | 这些人的 `visits` 条数 |
| **任务完成率** | 这些人的任务里 `status='done'` ÷ 非草稿任务数（**任务终态只有 `done`**，不是 finished） |
| **带来入商城客户** | 这些人的**拜访结果**选了 `加入商城` / `已签约商城` 的**去重客户数** |

🔴 **刻意不用**"客户档案的签约业务员" —— 那是客户表「业务负责人」**原值**（853 家是 `快餐盒c聚火配送🔥` 这种**组名**），
与 `users` 姓名**根本对不上**；混进来会让"推荐贡献"和"客户归属"两个口径打架。

## 六、防呆（已实现）

| 风险 | 处理 |
|---|---|
| 伪造 `ref` | 云端强制校验必须能查到 user；查不到**静默忽略** |
| 互相推荐（A→B→A） | `setUserReferrer` 沿推荐链往上找，链上出现自己就拒绝 |
| 选自己当自己的推荐人 | 直接拒绝 |
| 老板**免审核通道**（`BOSS_PHONE` 注册） | 不记推荐人（它不是注册申请，直接激活） |
| 游客（trial） | 不记推荐人（体验账号，之后会清） |
| 推荐人离职/改名 | 显示用 `referrerName` 快照，不依赖对方账号 |

## 八、怎么验证（真机）

1. 业务员 A 在小程序点首页右上角**分享** → 发给 B
2. B 点开 → 填姓名 + 手机号注册
3. 后台「⏳ 待审核」应看到 B 的**推荐人 = A**（🔗）
4. 通过后 →「🏃 业务员」里 B 的推荐人列显示 A；A 那行多出「拉了 1 人」
5. 切「📊 推荐排行」→ 能看到 A 的统计
6. **存量补录**：在某人行点「设置」→ 下拉选推荐人 → 保存 → 显示 `✏️ 手工`

⚠️ **两个已知限制**（不是 bug）：
- 新人如果不是点分享卡片进来（自己搜索/扫码/别人口头告诉他）→ 拿不到推荐人，只能事后手工补
- 微信分享参数只在"通过该分享卡片打开小程序"时有效
